Технічна специфікація · версія 1.0

Завантаження чинної редакції нормативних документів

Технічне завдання на розробку локального Windows-застосунку ZakonDownloader. Програма отримує публічно доступний текст документа з zakon.rada.gov.ua, формує файл .txt, веде історію операцій та технічні журнали.

Мова розробки Python 3.11+
Цільова ОС Windows 10 / 11, 64-bit
Формат постачання Автономний .exe

01. Межі та принципи роботи

1.1. Функціональна мета

Програма повинна:

  1. Приймати одне пряме URL-посилання на документ із домену zakon.rada.gov.ua.
  2. Перевіряти коректність та допустимість URL.
  3. Отримувати публічно доступний HTML-вміст сторінки дозволеними засобами.
  4. Визначати та зберігати повний текст чинної редакції документа.
  5. Витягувати метадані: назву, тип, номер, дати, статус, URL-джерело.
  6. Зберігати текст у форматі .txt у кодуванні UTF-8.
  7. Вести постійну історію всіх запусків та окремі технічні логи.
  8. Дозволяти користувачу сформувати зведений файл усіх логів.

1.2. Основний користувацький сценарій

Користувач запускає ZakonDownloader.exe, вставляє пряме посилання на документ, натискає кнопку «Завантажити документ» і отримує повідомлення про результат. У разі успіху програма створює текстовий файл у заздалегідь визначеній папці.

1.3. Межі безпеки та законності

Принципова вимога Програма працює лише з відкрито доступними даними та не повинна обходити технічні або правові обмеження ресурсу.

Застосунок не повинен:

  • обходити CAPTCHA, антибот-захист або WAF;
  • обходити авторизацію, платний доступ чи обмеження доступу;
  • використовувати проксі, ротацію IP або браузерну автоматизацію для уникнення захисту;
  • підміняти технічні механізми безпеки;
  • використовувати чужі облікові дані або секрети.

Допустимі способи отримання тексту:

  • публічна HTML-сторінка;
  • офіційно доступний API або механізм експорту — якщо він існує й доступний публічно;
  • HTTP-сесія, стандартні cookies та коректні HTTP-заголовки;
  • контрольовані повторні спроби для тимчасових технічних збоїв;
  • дотримання обмеження частоти запитів.

02. Функціональні вимоги

2.1. Структура графічного інтерфейсу

Інтерфейс має бути українською мовою та складатися з таких вкладок:

Завантаження Історія Журнали / логи Налаштування Про програму

2.2. Вкладка «Завантаження»

Елемент Призначення
Поле URL Введення прямого посилання на сторінку документа.
«Вставити з буфера» Вставляє URL із буфера обміну Windows.
«Завантажити документ» Запускає валідацію, отримання, парсинг і збереження документа.
Індикатор процесу Відображає стан виконання без блокування інтерфейсу.
Область результату Містить статус, назву документа, шлях до файла або опис помилки.
«Відкрити файл» Активна лише після успішного створення документа.
«Відкрити папку документів» Відкриває папку зі збереженими файлами.

2.3. Логіка обробки URL

  1. Перевірити, що поле URL не порожнє.
  2. Переконатися, що URL починається з https://.
  3. Переконатися, що домен — zakon.rada.gov.ua.
  4. Створити запис в історії зі статусом «Розпочато».
  5. Запустити отримання документа у фоновому потоці.
  6. Отримати HTML, перевірити відповідь сервера та визначити тип результату.
  7. Витягнути метадані й повний текст чинної редакції.
  8. Створити та зберегти .txt-файл.
  9. Оновити історію та журнал операції.
  10. Показати користувачу фінальне повідомлення.

2.4. Політика мережевих запитів

Параметр Значення
Таймаут підключення10 секунд
Таймаут читання відповіді30 секунд
Максимальна кількість спроб3
Пауза між повторними спробами2, 5, 10 секунд
Стратегія повторівExponential backoff
Звичайна мінімальна пауза між запитами1–2 секунди
Паралельні завантаженняНе підтримуються; один документ за раз

Повторні спроби дозволені для тимчасових мережевих збоїв та відповідей сервера класу 5xx. Для 403, 429, CAPTCHA або сторінки обмеження доступу застосунок не виконує обхід і завершує операцію контрольованим повідомленням.

2.5. Визначення чинної редакції

  1. Перевірити наявність позначки «чинна редакція», «поточна редакція» або дати редакції.
  2. Якщо URL вже веде на чинну редакцію — використовувати саме цей текст.
  3. Якщо на сторінці є офіційне відкрите посилання на чинну редакцію — перейти за ним.
  4. Якщо дату чинної редакції встановити неможливо — файл не створювати.
Захист від некоректних даних Якщо програма не може однозначно підтвердити дату чинної редакції, вона не зберігає документ із потенційно неправдивою назвою файла.

2.6. Вимоги до парсингу тексту

Парсер має вилучати з HTML-сторінки:

  • заголовок, преамбулу, розділи, статті, частини, пункти та підпункти;
  • прикінцеві й перехідні положення;
  • примітки та текстові таблиці, якщо вони належать до документа.

Парсер має виключати:

  • навігацію, меню, кнопки й службові блоки;
  • рекламу та сторонній вміст;
  • JavaScript, CSS і технічні елементи сторінки;
  • дубльовані заголовки та службові посилання.

2.7. Форматування й кодування

  • Кодування вихідного файла: UTF-8 без BOM.
  • Кирилиця і латиниця мають коректно відображатися у сучасних редакторах.
  • HTML-сутності мають декодуватися.
  • Нерозривні пробіли необхідно замінювати звичайними.
  • Кілька порожніх рядків поспіль скорочуються максимум до двох.
  • Логічна структура абзаців і заголовків має зберігатися.
  • Таблиці, якщо можливо, перетворюються у текст з розділювачем |.

2.8. Ім’я та вміст файлу

Шаблон назви:

<transliterovana_nazva_dokumenta>_<ДД.ММ.РРРР>.txt

Приклад:

pro_zahyst_personalnyh_danyh_01.01.2024.txt

Правила формування:

  • назва транслітерується з української в латиницю;
  • слова розділяються символом _;
  • використовується нижній регістр;
  • заборонені символи Windows видаляються або замінюються;
  • максимальна рекомендована довжина назви без розширення — 180 символів;
  • за наявності файла з таким самим ім’ям він перезаписується;
  • за відсутності назви використовується резервний шаблон document_<id>_<date>.txt.

Шаблон вмісту файла

================================================================
МЕТАДАНІ ДОКУМЕНТА

03. Історія операцій та журнали

3.1. Історія операцій

Історія має зберігатися локально в базі SQLite, бути доступною у вкладці «Історія» та не очищуватися через графічний інтерфейс.

Поле Зміст
IDУнікальний ідентифікатор операції.
Дата і час запускуЧас початку обробки URL.
Дата і час завершенняЧас успіху або завершення з помилкою.
URLПосилання, введене користувачем.
Назва та номерЗаповнюються, якщо документ вдалося розпізнати.
Дата чинної редакціїДата, що використовується у назві файла.
РезультатУспішно, помилка, не знайдено, доступ обмежено тощо.
Текст помилкиКороткий опис причини невдачі.
Шлях до файлаШлях до створеного TXT, якщо операція успішна.
Версія програмиВерсія ZakonDownloader на момент виконання.

Вкладка історії повинна підтримувати:

  • пошук за назвою, URL, номером документа або статусом;
  • фільтрацію за статусом і датою;
  • сортування за датою;
  • відкриття пов’язаного файла, папки або логу;
  • оновлення таблиці.
Незмінність історії У GUI не передбачаються кнопки видалення, очищення або редагування історичних записів.

3.2. Логи

Логи створюються для кожної операції — і для успішної, і для неуспішної.

Підтримувані рівні:

INFO WARNING ERROR DEBUG

У технічний лог необхідно записувати:

  • дату, час, ідентифікатор операції та URL;
  • етап виконання;
  • HTTP-статус, якщо він доступний;
  • кількість спроб;
  • назву та шлях створеного файла;
  • опис помилки і traceback у разі винятку;
  • версію застосунку.
Обмеження журналювання Логи не повинні містити cookies у відкритому вигляді, паролі, токени, секрети чи інші чутливі дані.

3.3. Об’єднання логів

У вкладці «Журнали / логи» розміщується кнопка «Створити зведений файл логів».

  1. Програма знаходить усі файли з папки логів.
  2. Упорядковує їх хронологічно.
  3. Створює один TXT-файл із заголовком та переліком джерел.
  4. Зберігає результат у папці data/exported_logs/.
  5. Показує шлях до файла та кнопку відкриття папки.
combined_log_ДД.ММ.РРРР_ГГ-ММ-СС.txt

4.2. Надійність і продуктивність

  • Інтерфейс не повинен зависати під час мережевих операцій.
  • Усі запити виконуються у фоновому потоці через QThread або QRunnable.
  • Критичні винятки обробляються та не завершують роботу GUI аварійно.

07. Черговість написання коду

Етап 1. Ініціалізація репозиторію

  • Створити Git-репозиторій, віртуальне середовище та структуру папок.
  • Додати залежності: PySide6, HTTP-клієнт, BeautifulSoup4, lxml, pytest, PyInstaller.
  • Створити README.md, .gitignore, pyproject.toml.

Етап 2. Конфігурація, шляхи та системне логування

  • Реалізувати константи, конфігурацію та створення папок data/....
  • Налаштувати файлові логи, формат подій та ротацію логів.

Етап 3. База історії

  • Створити SQLite-базу та таблицю history_entries.
  • Реалізувати додавання, оновлення, пошук і фільтрацію записів.
  • Покрити репозиторій unit-тестами.

Етап 4. Валідація URL і допоміжні функції

  • Перевірка URL та домену.
  • Транслітерація українського тексту.

08. Критерії приймання

  1. EXE запускається на Windows 10/11 без установленого Python.
  2. Користувач може вставити один прямий URL документа.
  3. Програма не приймає URL зі сторонніх доменів.
  4. Для доступного документа створюється TXT у data/documents.
  5. Файл має кодування UTF-8 і коректно відображає кирилицю та латиницю.
  6. Назва файла відповідає шаблону транслітерованої назви та дати ДД.ММ.РРРР.
  7. За збігу назви існуючий файл перезаписується.
  8. На початку TXT є окремий блок метаданих.
  9. У файл не потрапляють меню, кнопки та інші службові HTML-елементи.
  10. Кожна спроба потрапляє в локальну історію та технічний лог.
  11. Історія зберігається після перезапуску й не має функції очищення через GUI.
  12. Користувач може сформувати зведений файл логів.
  13. За обмеження доступу програма повідомляє користувача, фіксує подію та не обходить захист.
  14. Інтерфейс не зависає під час завантаження.
